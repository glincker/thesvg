# Contributing flags

How to add a missing flag or fix a wrong or outdated one. Everything in `public/icons/flag-*`, `packages/flags/src/data` and `THIRD_PARTY_NOTICES.md` is generated by `scripts/flags/generate-flags.mjs`. Never edit those files by hand: change the source mapping, rerun the generator and commit the result.

## The quick way

Open a [missing or wrong flag issue](https://github.com/glincker/thesvg/issues/new?template=flag_fix.yml) with the source link and its license. A maintainer can take it from there.

## Adding or fixing a flag in a pull request

1. Find a source with an accepted license (below). Download the SVG outside the repository.
2. Edit `scripts/flags/generate-flags.mjs`: add the flag to `EXTRAS` (name, parent, languages, native name, `kind`) and, if it is not in the default sources, a `files` entry. For a Wikimedia Commons file give `file`, `title`, `author`, `license` and `url`; the license must be `Public domain`, `CC0`, `MIT` or `Apache-2.0`. For a new upstream repository add it to `SOURCES` with its own license entry and `SOURCE_LICENSE_FILES`. The generator aborts, and changes nothing, when a source has no license entry.
3. Add search aliases in `scripts/flags/flag-aliases.json` and, if the flag is a locale hint, an entry in `packages/flags/src/locale.ts`.
4. Run the generator: `node scripts/flags/generate-flags.mjs --fi <flag-icons clone> --cf <circle-flags clone> [--commons <dir of Commons files>]`. Use `--report changed.json` to list the flags whose files changed.
5. Run `pnpm --filter @thesvg/flags test`, `pnpm test`, and the checks in the PR checklist.

## Accepted licenses

MIT, CC0, public domain (with proof, for example the Commons file page checked through its API on the day you add it) and Apache 2.0 (the notice must ship in `THIRD_PARTY_NOTICES.md`, which the generator writes).

## Rejected

Unclear licenses, traced or copyrighted artwork, share-alike licenses such as CC BY-SA, sources that need attribution inside the file, and contested entities without a clean source. A flag is a public symbol and the catalog makes no statement about sovereignty; the ISO 3166-1 list is the baseline.

## Files carry no credit text

The SVG files contain no comments, metadata, titles or generator strings. Credit lives at package and repository level only: `THIRD_PARTY_NOTICES.md` (full license texts), `packages/flags/src/data/licenses.json` (every file mapped to its upstream path) and the license section of the package README. A test fails if a flag file lacks a manifest entry, if a source named in the manifest is missing from the notices, or if a file contains credit text. Do not weaken any of it.

## PR checklist

- [ ] License entry in the generator and a line in `THIRD_PARTY_NOTICES.md` (generated).
- [ ] Every new file is under 51,200 bytes, or the exact file names are added to the documented exemption lists in `scripts/validate-icons.ts` and `validate-svg.yml` with the reason. Accuracy wins over size, but compaction is tried first and guarded by a pixel fidelity check (`FLAG_FIDELITY_MAX`).
- [ ] Aliases (names, native name, former names) and the locale mapping if relevant.
- [ ] Counts in docs and llms files regenerated (the generator and `generate-llms-txt.ts` do it); drift tests pass.
- [ ] No em or en dashes, no credit text in SVGs.

## Pulling upstream updates

Point the generator at a newer upstream commit: `git -C <clone> pull`, then run the generator with `--fi` and `--cf` and `--report changed.json`. The pinned commits and access dates update in `licenses.json` and `THIRD_PARTY_NOTICES.md` only when a commit changes. Review the diff of the changed flags (the report lists them) before committing. Flags that changed recently should be spot-checked against an official source.
